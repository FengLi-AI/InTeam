# InTeam v1.9：任务准备 Agent 与检索修复

## 原来与现在

原来主要是企业问答：用户提问，系统从 Dify 知识库查资料后回答；用户可以确认建议，把它加入自己的行动清单。

现在保留企业问答，并增加“任务准备 Agent”。用户给出一个目标，例如“给中学生准备 5 分钟能源展厅讲解”，模型会自己决定先搜索哪些资料、是否继续阅读全文，再整理准备材料。支持展厅讲解和企业上手两个场景。

标题栏可以切换两种模式；两者使用同一种自适应输入框，Agent 发送按钮采用深灰色。过程、参考资料、待补充信息和历史任务可以查看；用户可以继续修改上一轮目标或停止任务。

## 为什么算 Agent

Agent Loop（模型根据工具结果决定下一步的循环）在后端运行：

1. 接收目标和必要上下文。
2. 模型决定调用 `search_knowledge`（搜索资料）或 `read_document`（阅读资料）。
3. 后端校验参数、权限和资料范围，把真实工具结果交回模型。
4. 模型可以继续查，也可以结束并生成准备材料。

这不是预先固定的“搜索一次就生成”的流程。循环最多 8 轮、8 次工具调用，最长 120 秒；这些限制避免无限运行和失控消耗。

Agent Harness（支撑模型可靠执行任务的程序）包括工具白名单、参数校验、资料权限、任务历史、停止控制、执行记录、资料引用校验和人工确认。模型不能直接发消息、操作设备或替用户创建正式行动。

“准备材料已生成”“需要你补充任务信息”“资料不足”“现场需确认”分别表达不同情况，不再把所有提醒统称为任务失败。

## Dify 修复

企业问答继续走 Dify。此次发现部分文档停用，以及模型重排后有效候选被丢弃的问题。岗位资料还出现标题与正文分离，导致 30/60/90 天目标混淆；已改为保留完整短文档，项目资料采用完整父段返回。恢复文档并修复分段后，最终采用混合检索的权重排序：语义 0.7、关键词 0.3，召回上限 20，不启用分数阈值。当前知识库规模较小，提高召回上限可以减少漏查；扩大资料规模时需要重新评测上下文长度、重复片段、费用和响应时间。

Embedding（把文字转成可比较向量）仍使用已接入 AI Hub Mix 的 `qwen3-embedding-4b`，回答与结构化建议仍使用该平台的 `deepseek-v4-flash`。未新增其他模型平台。任务准备 Agent 使用用户配置的 DeepSeek 接口。

后端对检索空结果增加拦截：不能把无依据回答和行动建议当作可靠结果交给用户。有相关资料也不代表所有回答都正确，仍需通过真实问答案例检查。

## 部署与回退

后端新增一张 `agent_runs` 任务历史表，不覆盖原有用户与行动表。部署前应备份生产数据库，并在副本验证迁移。

单独部署后端前，在仓库根目录执行：

```bash
python backend/scripts/package_knowledge.py
```

该命令将企业资料打包到后端；展厅资料已放在后端目录内。部署包不得包含 `.env`、运行数据库、日志、测试会话或本地备份。生产密钥通过平台环境变量配置。

回退时需要同时核对前端版本、后端版本、Dify 发布版本和数据库迁移；不要用旧数据库覆盖新版本期间产生的用户记录。Git 标签只能恢复代码，不能替代生产数据备份。

## 面试时可以这样讲

“我以前做过面向企业的新员工上手和知识交付产品。InTeam 是我重新实现的一套产品，用来说明我怎么把业务场景、资料和 AI 能力组合起来。它原来主要解决‘我问你答’，这次增加任务准备 Agent，解决‘给你一个目标，你帮我查资料并整理准备材料’。

我没有做很大的通用 Agent，而是控制在展厅讲解、企业上手两个熟悉的场景。模型可以决定搜索和阅读顺序，后端负责权限、执行预算和过程记录。资料不足时明确说明，真正写入行动清单要经过用户确认。

我也遇到了真实的检索问题：接口返回成功，但重排后没有可用资料。所以我没有只看接口状态，而是检查检索输出、对比不同设置，再用问答案例验证。”

面试时应区分此前公司的工作经历、本次独立实现、测试结果和真实业务效果。当前能证明的是产品实现与验证能力，不能把测试结果说成企业客户的长期收益。
